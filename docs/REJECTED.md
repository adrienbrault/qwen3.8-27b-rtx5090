# Rejected configurations

This page lists configurations that were tried on this box and rejected, each with the number that ruled it out. Rows are dated and some refer to earlier served configurations (see [HISTORY.md](HISTORY.md)); benchmark-only rejects with their throughput deltas are in [`../bench/RESULTS.md`](../bench/RESULTS.md#rejected-configurations-with-numbers).

`turboquant_4bit_nc` was un-rejected 2026-07-15 and re-rejected for good 2026-07-20. It used to head this list ("4-bit keys destroy retrieval, 0/8"). That 0/8 was a confound, vLLM's async×spec-decode scheduler desync ([#42655](https://github.com/vllm-project/vllm/issues/42655)), not the 4-bit keys: with `--no-async-scheduling` it passed everything (8/8 all depths, 90/90 concurrent) and ran as the daily (the served configuration) for three days ([the reversal](HISTORY.md#turboquant_4bit_nc-became-the-daily-the-asyncspec-reversal)). It was then superseded on merit by fp8 KV (flat deep decode, no custom kernel), and a final re-audition on the modern tier stack closed it permanently: 563K-token pool, wrong 60K needle, dead under the concurrency "killer" (the concurrent burst gate) ([the final record](HISTORY.md#2026-07-20-lmcache-dramnvme-kv-tiers-added-to-the-daily)). Two points carry over: a "corrupts under concurrency" verdict below may still be a confound, and a 2.6× pool that fails retrieval is not usable.

| tried | why it was rejected |
|---|---|
| **RadixArk/Qwen3.8-27B-NVFP4** (ModelOpt mixed: MLP+lm_head NVFP4, attention + GDN projections FP8) as the target | Measured 2026-08-21 on the daily config (tiers + nvfp4 KV + V2): +15–20% single-stream decode (170.8 t/s c1, because FP8 GDN projections read half the bytes of saka's bf16), but −20% prefill (9.6K vs 12.8K t/s at 8K), −25% KV pool (231,818 vs 309,090 at 200K), cannot serve 262K at util 0.93, and tool-eval (tool-calling benchmark, tool-eval-bench) 90.5 ± 0.7 vs 92 ± 1.4 with a worse Context & State category. Agent workloads on this box are bound by pool, prefill and context, not single-stream decode. It suits a single-user chat box better. `results/2026-08-21-radixark-ab` |
| **nvfp4-FA2** (FlashInfer FA2 nvfp4 KV) | Works, but loses to `turboquant_4bit_nc` on every axis, and took far more work. The full nvfp4 KV path was built from the [jethac/vllm](https://github.com/jethac/vllm) branch plus [FlashInfer PR #3684](https://github.com/flashinfer-ai/flashinfer/pull/3684), with JIT-compiled sm120 kernels, the same nvfp4 TechPrototyper documented at a 416K pool. It is byte-identical, retrieval is clean, and it runs on the FlashInfer FA2 backend. But the stable pool is only 184K (+11% vs k8v4, weights-bound by this vision+MTP checkpoint; the 416K needs a lighter text-only model), decode is −8 to −23% (worst at deep single-stream, from FlashInfer disabling split-KV on 4-bit KV), tool-eval is 82, it OOMs at util 0.97 (needs 0.94), and it is a 2-unmerged-branch dev build with a ~15-min first-launch JIT compile. nvfp4-FA2 was built the hard way, and `turboquant_4bit_nc`, the same idea with a better result, was a preset flag on the image already in use. (`4bit_nc` has itself since been retired, see its row, which only strengthens this reject: the surviving fp8 daily needs no dev build at all.) |
| **smaller-bit TurboQuant presets** (`k3v4_nc`, `3bit_nc`) | Ruled out by the code's own PPL table. Perplexity delta vs bf16: **k8v4 +1.17% → 4bit_nc +2.71% → k3v4_nc +10.63% → 3bit_nc +20.59%.** Every preset smaller than `4bit_nc` quantizes the keys further (3-bit keys), and keys are the sensitive part: retrieval collapses. There is no 8-bit-key, smaller-value preset to try, because values are already at 4. `4bit_nc` is the smallest preset that keeps quality; quality drops sharply below it. |
| **`turboquant_4bit_nc`** | Re-rejected and closed permanently (see the paragraph above). It was un-rejected once the async×spec confound was removed (8/8 needles, 90/90 concurrent, ~235K pool; the daily 2026-07-15 → 18), then superseded by fp8 KV (flat deep decode, no custom kernel), and finally re-auditioned on the modern tier stack: **pool 563,888**, but with a wrong 60K needle (hybrid buffer co-location corruption) and a dead engine under the `pp8192×c8` concurrent burst. Revival needs a state-corruption fix, a concurrency fix, a deep-decode-crater fix and new LMCache serde for its packed layout, against a working fp8 tier stack. Not worth it. |
| **KVarN** (vLLM fork, 4-bit KV quant) | Disqualified under concurrency, the same failure class as TurboQuant. As the big-context alternate it passed every single-stream depth and tool test, then failed both ways under concurrent load: with MTP, a fatal CUDA device assert; without spec decode, `!!!!` garbage at 3 × 45K streams. Caveat: this predates the [#42655](https://github.com/vllm-project/vllm/issues/42655) async-confound finding and KVarN was never re-run with `--no-async-scheduling`. It does share the architecture the TurboQuant post-mortem identified (custom 4-bit forks bypass native varlen attention and rebuild block tables under batch-uniformity assumptions), and TurboQuant's own async-off re-audition still failed. Across every concurrency battery on this hybrid, only fp8 KV has stayed clean. |
| **`nvfp4` native KV cache** (2026-07: would not load; 2026-08-21: promoted; since 2026-08-28 the one-card configuration) | 2026-07: `head_size=256` had no FlashInfer nvfp4 backend on `sm_120` via the stock path. 2026-08-21: FlashInfer's FA2 sm120 kernels merged, [PR #49891](https://github.com/vllm-project/vllm/pull/49891) rebased, and a linear-V-scale store overlay was shown to be numerically required. On the V2 runner with the LMCache tiers it is the daily: pool 309K, needles, restart-proof and the "sean gate" (the concurrent-loader needle gate) clean, tool-eval 92. [NVFP4KV.md](archive/NVFP4KV.md). The remaining cost is about 2 tool-eval points vs fp8 on the plain profile. |
| **DFlash** speculative decoding | Works, but too constrained: measured and rejected. It requires a full source build of [PR #40898](https://github.com/vllm-project/vllm/pull/40898) (SWA draft support). Result with the z-lab draft for the previous model: **185 t/s single-stream**, 2.0× its no-spec baseline, a bigger uplift than MTP's ~1.6×. The costs: 21K max context (3.3 GB draft and bf16 KV only, because fp8 trips the branch's hybrid page-size assert, and the branch predates NVFP4-`lm_head` support so quantized targets are limited), no batch scaling (c4 aggregate ≈ c1), and ~3× slower prefill. MTP's draft head lives inside the weights, costs ~0, and keeps 200K+ context. Revisit if #40898 merges into nightly. |
| **DFlash2 on one card** (2026-08-21; on two cards it became the served configuration on 2026-08-31, see [HISTORY.md](HISTORY.md)) | [PR #52816](https://github.com/vllm-project/vllm/pull/52816) on the nightly with the `incoai/Qwen3.8-27B-DFlash2` drafter: 164 t/s single-stream (2.25× AR), tool-eval 91. MTP on the same V2 runner measured 160 t/s with 2.5× the context and +40% at c4. The drafter's KV is sized to max-len (~62K ceiling on 32 GB), and concurrent prefill collapses. [DFLASH2.md](archive/DFLASH2.md). |
| NVIDIA's official NVFP4 quant (2026-07, previous model) | ~2.6× slower prefill, 20–25% slower decode, fatter checkpoint (max ~150K ctx), and MTP crashes at moderate batch. The community quants measured better. |
| **`--async-scheduling`** (i.e. *not* passing `--no-async-scheduling`) | Rejected twice. First on throughput (c4 552 → 526). The larger reason: with MTP it desyncs the request-ID to batch-row mapping and corrupts KV ([#42655](https://github.com/vllm-project/vllm/issues/42655)), giving 0/8 retrieval on `4bit_nc` and ~10% intermittent on k8v4. `--no-async-scheduling` has been on every MTP daily since (worth about 1 tool-eval point on the 2026-08 stack). |
| [froggeric fixed chat templates](https://huggingface.co/froggeric/Qwen-Fixed-Chat-Templates) | The bundled template already scores **4/4** on a behavioural probe (single and parallel tool calls, chat→tool→chat, chat-after-tools). No measured gain. |
| `--max-num-batched-tokens 4096` (2026-07, TurboQuant era) | ~4× prefill regression (9.6K → 2.6K t/s) for +28K ctx on that stack. On the current stack `mnbt` is set by the LMCache chunk (2·chunk − 1). |
| `VLLM_TQ_KV_SPLITS` < 32 | Costs both c1 (139→132) and c8. Not the batching bottleneck. |
| `VLLM_NVFP4_GEMM_BACKEND=flashinfer-cutlass` | Already the nightly default. No-op. |
| **LMCache + TurboQuant KV** (`turboquant_k8v4`, persisted tier) | Composes, but the persisted L2 tier is lossy, so it was not shipped. k8v4 KV builds and runs under LMCache and stores land, but the L2 SSD reload silently drops long-context needles (7/7 miss): the format-10 kernel copies the standard 512-wide layout, not k8v4's 262-wide packed one. (`turboquant_4bit_nc` packs even tighter, so it would have been lossier still.) LMCache persistence only round-trips faithfully with fp8 KV. Full write-up: [`LMCACHE.md`](HISTORY.md#lmcache--k8v4-composes-but-the-persisted-tier-is-lossy-not-shipped). |

## Suffix decoding rejected on decode speed (2026-08-29)

vLLM 0.28's built-in suffix decoding (arctic-inference backend), measured on the v0.28 nvfp4 daily: quality held (tool-eval 88.5 ± 0.7 ×2) but **code decode fell to 31.2 t/s** (accepted-per-draft 0.185) vs 177–190 with MTP on the same engine, which is worse than no speculation. Pattern-matching speculation has nothing to match on fresh generation, and the method is boot-level, so it cannot be confined to the repetitive flows it was designed for. `results/2026-08-29-r115-misc`.
