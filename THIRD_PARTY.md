## GPU driver P2P (dual-5090 host config)

The serving host runs [QuixiAI/open-gpu-kernel-modules](https://github.com/QuixiAI/open-gpu-kernel-modules) (Eric Hartford) — NVIDIA's open GPU kernel modules (dual MIT/GPL) with PCIe peer-to-peer force-enabled for consumer GeForce cards. The technique originates with [tinygrad / George Hotz's P2P patch](https://github.com/tinygrad/open-gpu-kernel-modules), later simplified by **aikitoria**, and ported to the 610 driver series with Blackwell support by QuixiAI. `scripts/gpu-p2p-610.sh` (ours, MIT) automates their install on Ubuntu, and the `RMForceStaticBar1=1` + `NVreg_EnableResizableBar=1` regkey pair plus the `iommu=pt` requirement come from that fork's documentation and our validation on a 2x RTX 5090 / X870 box.

Ported as `0133-gdn-packed-decode-bv16-v0290.diff` with a local `VLLM_SM12X_GDN_PACKED_BV` override (the PR's selector requires 16 value heads; this model has 48). - **[vllm#54163](https://github.com/vllm-project/vllm/pull/54163)** (Ledgero) — DFlash/DSpark drafters draft from their own KV cache and never write target blocks, so the KV cache manager must not apply eagle block handling to them. `0134-dflash-no-eagle-block-drop-v0290.diff` is an rc1-native port of the predicate (the PR targets a newer main); without it v0.29.0rc1 + Qwen3.8-27B + DFlash2 serves zero prefix-cache hits and the disk tier stores without ever serving (bench/RESULTS.md R165). Verdict (R165b): proven — warm revisit 0.166 s / 53,248 hits with 0134 vs 7.5 s / 0 hits without. The root-cause analysis in that PR and in the closed [vllm#54041](https://github.com/vllm-project/vllm/pull/54041) (positive666) is what pointed at the mechanism.
- The v0.29.0rc1 rebase of the whole chain (`patches-v0290/`, NOTES16.md) was produced with codex (gpt-5.6-sol) from local source dumps; every build and measurement runs on the host by the maintainer.

- **[vllm#53981](https://github.com/vllm-project/vllm/pull/53981)** (waizuichougou) — routes directly constructed `VocabParallelEmbedding` modules through vLLM's existing UVA CPU offloader, so `--offload-backend uva --cpu-offload-gb N --cpu-offload-params embed_tokens` reaches the input embedding table (built outside `make_layers`, where the selector silently matched nothing). Fixes [vllm#53931](https://github.com/vllm-project/vllm/issues/53931) (webcodes-cz), which was filed with exactly this model as the repro. Ported verbatim minus its tests hunk as `0135-embed-uva-offload-v0290.diff` (applies clean to rc1; does not apply to v0.28.0). The idea of keeping the 2.37 GiB BF16 table in pinned host RAM and gathering rows over PCIe was brought to our attention by [sglang#37826](https://github.com/sgl-project/sglang/pull/37826) (nbald), which does the same with a Triton host gather; in vLLM the plain `F.embedding` on the UVA view plays that role. Source review of the port for our TP=2 / DFlash2 / pinned-pool shape: `patches-v0290/NOTES18.md` (codex, gpt-5.6-sol). Verdict (R167, 2026-09-03): validated on the rc1 chain — +9.3% KV pool with nvfp4 KV (+82,811 tokens, the whole 1.18 GiB shard) and +8.4% with fp8, no measurable decode or fidelity cost at c1/c8/30K context, needles clean. Not on the daily yet: the daily runs v0.28, where the patch does not apply, and the rc1 nvfp4 route had a deep-context decode regression — attributed the same evening to FlashInfer 0.6.18's NVFP4 split-KV guard (next entry).

- **FlashInfer 0.6.18 `_nvfp4_kv_requires_disabled_split_kv`** ([flashinfer-ai/flashinfer](https://github.com/flashinfer-ai/flashinfer), `flashinfer/prefill.py`, first shipped in the 0.6.17/0.6.18 window) — the FA2 paged-prefill wrapper overrides the caller's `disable_split_kv=False` for packed-NVFP4 KV, as an empirical workaround for corrupted outputs when a short query attends a long KV range. On our route (speculative verification = 10 query tokens → prefill wrapper) it turns 30K-context decode from 144 to 29 tok/s (R167/R168). `0136-opt-in-nvfp4-prefill-split-kv-v0290.diff` (codex, gpt-5.6-sol, from our BRIEF19; source analysis in `patches-v0290/NOTES19.md`) is an opt-in knob `VLLM_SM12X_NVFP4_PREFILL_SPLIT_KV=1` that restores the 0.6.16.post3 behaviour on the SM12x NVFP4 route only; off by default because the corruption FlashInfer saw is the family our Bug B dodge exists for. Verdict (r168b, 2026-09-03): with the knob on, rc2 decodes 141.9 tok/s at 30K context (27.4 off; 143 on v0.28), short-context speed unchanged, needles 12/12 to 220K, zero error lines, and the teacher-forced ruler is bit-identical on vs off — because prompt-logprob scoring is a long-query prefill that FlashInfer never splits, i.e. that ruler cannot see the knob at all. The decode-path adjudication (T=0 generations at 30K and a cached-prefix depth ladder, on vs off) is r168c.
- **`0137-fs-tier-eviction-v0290.diff` — LRU eviction inside vLLM's filesystem KV tier** (codex, gpt-5.6-sol, from our BRIEF20; design notes `patches-v0290/NOTES20.md`, tests in the patch, `verify-0137.sh`). vLLM's `FileSystemTierManager` (the `TieringOffloadingSpec` fs secondary tier, 0.28 and 0.29) writes forever and never deletes: the tier fills the filesystem, stores fail with ENOSPC (logged, engine alive) and a restart cannot come back. The patch adds `max_capacity_gb` / `evict_high_ratio` / `evict_low_ratio` / `min_free_gb` / `evict_scope` to the tier config, a startup scan, LRU on lookup/load/store, and pins for files a lookup, a hit request or a transfer job references (the offloading worker asserts on a failed load, so an external sweeper is unsafe under load). Applies `--fuzz=0` to v0.28.0, rc1 and rc2. Verdict: pending r170 (flood under a 24 GB cap on both the rc2 candidate and the v0.28 daily image).
