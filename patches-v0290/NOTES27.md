R144 is an experimental compiler-to-PCIe IPC fusion patch for the supplied 0.29.0rc2 tree. It is NOT a verified bitwise-equivalent or benchmarked implementation. Offline verification covers patch application, Python syntax, knob parsing, row ownership and scratch bounds. CUDA compilation, the actual compiler matches, numerical identity and graph execution require the box. In particular, the brief's universal bitwise norm requirement cannot be established from layernorm.py alone: the selected IR lowering/Inductor reduction tree is not fixed by that file. The delivered probe defaults to rejecting any bit mismatch. Do not promote on an approximate comparison alone.

The route is the existing AllReduceFusedAddGemmaRMSNormPattern, replacing all_reduce → fused_add_rms_norm(weight.float()+1). The new knob automatically schedules AllReduceFusionPass, independently of fuse_allreduce_rms. The PCIe branch registers only the Gemma-with-residual pattern at epsilon 1e-5 and 1e-6; it allocates no TensorRT-LLM workspace. It includes the existing first-output-only pattern (final model norm). Ordinary RMSNorm/DFlash computation is outside the target pattern; an explicitly supplied DFlash2DraftModel compilation config is excluded. Model forwards are unchanged. Extra users of an all-reduce result, including DFlash auxiliary hidden-state collection, can prevent a pattern match; it would be incorrect to defer those reductions across layer boundaries manually. Count actual matches/kernels rather than assuming 128.

In this dump, CUDA AllReduceFusionPass uses FlashInfer's trtllm fused op, and flashinfer_all_reduce.py selects a trtllm or mnnvl workspace. Neither calls the 0138 PCIe workspace. flashinfer_max_size nominally accepts TP2/4/8/16, but its default capability table covers 90/100/103/107, not 120: SM120 has no default size. Token limit is max bytes / (widest target-or-draft hidden * dtype bytes), capped by scheduler tokens. Patterns use the model dtype, with a dedicated Gemma pattern for fp32 gamma. ROCm has AITER fused collectives, inapplicable here. Enabling the old compiler flag does not constitute a working fused TP2 PCIe path. R186's historical TP2 disable should not be confused with a blanket TP2 rejection in this patched source.

Grammar is exactly VLLM_SM12X_PCIE_IPC_AR_FUSED_NORM unset/0 (disabled) or 1 (enabled), with VLLM_SM12X_PCIE_IPC_AR=1 required. Empty strings, true, 01, 2, etc. raise. Both ranks must use identical knobs. Existing 0138 admission supplies TP2, RTX5090/SM120, CUDA13, bf16/H5120, no MoE/LoRA/sleep/overlapping parallel execution, and only sequential DFlash speculation. Fusion also rejects SP, batch-invariance mode and non-Qwen3.5-dense target configs. Runtime arguments require contiguous bf16 [M,5120] inputs/residual, contiguous bf16 or fp32 [5120] weight on the workspace device, positive supported epsilon and 16-byte input alignment. Unsupported arguments raise; there is no exception-driven collective fallback. Epsilon pattern coverage is 1e-5/1e-6 (the supplied model uses 1e-6).

Only the requested capacity exception falls back: M>320 (max_numel=1,638,400) or empty tensors use the original dispatcher plus Gemma IR norm, logging once. A compiler range outside the scheduler range is not rewritten. M=2048 is explicitly an unfused benchmark case, not a fused-kernel speed claim. The runtime proof line (local scope, once per process, including capture warmup) is:

`PCIe IPC fused norm ACTIVE: TP2 bf16 H5120 max_rows=320 R144`

The fallback line is `PCIe IPC fused norm: capacity fallback to unfused`. Grep the ACTIVE string in docker logs; two TP ranks should each emit it. Presence proves runtime dispatch during warmup/capture, not replay speed. Absence after decode means no exercised fusion; do not treat that as a negative performance result. Also inspect compiler match logs and trace kernel names containing pcie_norm_kernel. The benchmark directly calls the extension and does not prove the vLLM pattern matched.

The derivative uses the same block scratch, fixed max-capacity double-buffer epoch offsets, per-call scratch-state counter, transmitted +0→-0 sentinel conversion, volatile remote publish/local polling, packed bf16 addition and zero-reset as ipc_tp2_remote_push_kernel. It uses min(M,128) CTAs of 256 threads, with each CTA owning complete rows; rows beyond 128 are CTA-strided. This changes the tuned launch geometry deliberately and does not label it an R184 measured tactic. No cross-CTA norm barrier is needed. All CTAs still advance the shared scratch epoch even when per-CTA row counts differ. No PDL is enabled. Arbitrary CUDA graph replays must remain serialized, sharing the original communicator's capture ownership/context. The fused op performs no host synchronization, metadata collectives, lazy preparation or new IPC allocation; output allocations are normal graph-pool allocations during capture. One stream only: eager calls on a different recorded ownership stream raise. Peer loss or unequal collective sequences can spin indefinitely, as in the original kernel. Shape-bound tests do not establish concurrency safety.

Numerics follow GemmaRMSNorm.forward_native and ir/ops/layernorm.py:fused_add_rms_norm: packed AR first rounds to bf16; convert that value and residual to fp32, add, store residual bf16, but compute variance from the UNROUNDED fp32 sum; multiply normalized fp32 by (1+float(weight)), then cast output bf16. Adding the residual in bf16 before computing variance would be wrong here. The kernel explicitly separates fp32 multiply/add to avoid FMA contraction in the variance accumulation. It uses a 256-thread tree of per-thread pack sums and rsqrtf; this can differ from the compiled reference's variance summation tree or reciprocal approximation, yielding bf16 output differences near rounding boundaries. No additional intentional bf16 rounding point is introduced. Residual bit equality is expected for finite operands with the same AR result, but universal NaN payload/signed-zero identity is not promised by the existing sentinel protocol either. The bitwise requirement remains an on-box acceptance gate, not a completed claim.

## R190e addendum (2026-09-05 06:00 UTC, engine boot failure, fixed in-place)

The first engine arm with `VLLM_SM12X_PCIE_IPC_AR_FUSED_NORM=1` never booted: the strict ownership check in `pcie_ipc_fused_norm.py` raised `PCIe fused norm requires the workspace ownership stream` inside `capture_model`'s eager warmup forward (`forward_fn(CUDAGraphMode.NONE)`), on both pins. vLLM's profile run and its capture warmup run on different current streams, so the second eager call always sees a stream other than the one the first call bound. The workspace's own `all_reduce` tolerates exactly this through `_check_stream()` (no-op while capturing; synchronize + rebind on an eager stream change). The fused op now calls `ws._check_stream()` instead of the strict check; nothing else in 0144 changed. The "one stream only: eager calls on a different recorded ownership stream raise" statement above is therefore superseded — the fused op follows the all_reduce policy.

## R190e second addendum (2026-09-05 07:20 UTC, second engine boot failure, fixed in-place)
