The R205 image booted with a logging overlay bind-mounted over `kv_cache_manager.py` and `kv_cache_coordinator.py` (no rebuild): the input and result of `get_computed_blocks`, the per-group hit lengths inside the hybrid coordinator's `find_longest_cache_hit`, and the per-manager token counts of `cache_blocks`. Layout on this route: block 1,472 = hash unit, hybrid coordinator, three Mamba managers (no longer flagged as drafter groups after 0154) and one full-attention manager flagged as the drafter's, `use_eagle_kv_block_drop` true, one prefill lookahead token.

One 6,000-token prompt (four full blocks) sent three times: send 1 hit 0; send 2 hit 0 with the full-attention group finding three blocks (the fourth dropped), the three Mamba groups finding 0, the coordinator reconciling to 0 and pinning the shared-prefix junction at 4,416 tokens; send 3 hit 4,416. The same shape at 53,455 tokens (send 2 uncached 51,520 = 35 × 1,472) and in the R205 needle gate (second re-ask hit 129,536 = 88 × 1,472 on a prompt of 89 full blocks). Every hit that ever happened was (last full block − 1) × block and only on the third send. API, answer length and inter-send gap made no difference.

The mechanism, from the tree. `Scheduler._mamba_block_aligned_split` backs the last cacheable position off by one block when the drafter's group drops its last matching block ("FullAttn prunes the last matching block, so back off one block to avoid a Mamba cache miss"), so the reusable Mamba state of a prompt is checkpointed in state block N − 2. `SingleTypeKVCacheManager.cache_blocks` builds the retained boundaries as `num_prompt_tokens − 1` (plus any shared-prefix junction) and `reachable_block_mask` marks block N − 1 only; the mask's own comment says "draft models have no mamba layers, so no eagle shift". The retention policy of this tree defaults to `prefix_cache_retention_interval = 0` (semantic checkpoints only; `None` is dense), so block N − 2 is never hashed, every Mamba group misses, and the junction pin of the second send is what marks N − 2 for the third. DFlash never drops a block, so N − 1 is the right block and the served configuration was never affected.

Why the offline scheduler said otherwise in R205: the synthetic KV-cache config of vLLM's scheduler tests leaves the retention interval at `None` (dense, mask skipped). With `--retention 0` the real Scheduler driven offline on the live prompt shape (53,468 tokens, block = hash 1,552, chunk 8,192, MTP draft length 3) reproduces the live symptom: each Mamba group caches 0 hashes and the second send hits 0; without speculative decoding each Mamba group caches block 33 and the second send hits 52,768.

Patch 0158 (`patches-v0290/0158-eagle-drop-mamba-replay-boundary-v0290.diff`, 66 lines): the coordinator marks every group that does not drop its own last block when the scheduler applies the drop, and the base `cache_blocks` then also retains the boundary `num_prompt_tokens − 1 − scheduler_block_size`, the block the scheduler checkpoints. No memory cost: it marks the block that exists instead of the empty one. Offline with 0158 and retention 0: each Mamba group caches block 32 and the second send hits 51,216, identical to the dense-retention control; the no-speculation arm is unchanged. Edge not fixed: a prompt of exactly k × block tokens is checkpointed at P − B while the mask marks P − 2B, the same pre-existing edge as without a drafter (one prompt in 1,472).
