## The layer serves one GEMM shape of the MTP verify step

Each of the model's 48 Gated DeltaNet layers projects the hidden state to its `b` and `a` gates through `in_proj_ba`, a bias-free bf16 linear of 5,120 inputs and 96 outputs, 48 per card at tensor parallel 2. With the MTP head at 3 draft tokens, one sequence's verify step feeds it 4 rows: M=4, N=48, K=5,120. vLLM serves that call with its default unquantized GEMM, `torch.nn.functional.linear` on cuBLAS.

With `VLLM_SM12X_BA_M4=1`, [L1a_BA4.diff](../../patches-v0310/ba4/L1a_BA4.diff) routes `UnquantizedLinearMethod.apply` through `vllm_ba4.runtime.try_apply` for layers whose prefix ends in `.linear_attn.in_proj_ba`. The call goes to a Triton kernel only for a bf16 `[4, 5120]` input with the validated stride and alignment on an SM120 card at tensor parallel 2; every other shape and layer returns to the original GEMM. The candidate kernels ([kernels.py](../../patches-v0310/ba4/vllm_ba4/kernels.py)) multiply the bf16 operands in FP32, reduce the 5,120 products in FP32 and cast once to bf16, as a direct kernel or a split-K kernel with a second reduction launch. Under `torch.compile`, the piecewise backend compiles the batch-size-4 specialization with the BA4 op and restores the original linear in the graphs of every other size.

Each rank admits each layer at boot from a report and a launch binding ([policy.py](../../patches-v0310/ba4/vllm_ba4/policy.py), [runtime.py](../../patches-v0310/ba4/vllm_ba4/runtime.py)). The report carries the per-candidate measurements of a serving-path profile and the selected kernel, the device fingerprint (GPU name and UUID, compute capability, Torch, CUDA and Triton versions, BLAS settings), the SHA-256 of the installed `vllm_ba4` code and the SHA-256 of every layer's weight bytes. A layer is admitted only when the report's protocol and verdict pass, the selected kernel is the fastest correct graph-checked candidate, and the fingerprint, code hash and weight hash match the running process. An admitted layer logs `SM12X BA4 ACTIVE: prefix=<layer> rank=<r> pid=<pid> kernel=<selected>`; any mismatch logs `SM12X BA4 INACTIVE: ... reason=<reason>` and the layer keeps the original GEMM. The served reports came from two c1 profile runs on the serving host (results `2026-10-19-r27-audition-profile-055838-139066`, `2026-10-19-r27-audition-profile-064541-1580007`) through the harness's profile qualifier. The launcher does not fail the boot on an inactive layer; it reports how many of the 96 rank-layers are active.

Two earlier c1 code profiles of the layer (results `2026-10-19-r27-audition-profile-035809-2722537`, `2026-10-19-r27-audition-profile-041758-888801`, L1a boot then BA4 boot, 4,096-token generations) measured the unprofiled decode step at 12,530 → 11,077 µs and 12,533 → 11,075 µs, 11.6 % shorter in both, with draft acceptance means of 0.733 (L1a) and 0.726 (BA4). Those boots ran an earlier build of the layer in its profiling mode; the later builds changed admission only, and the profiling mode runs the same kernel and dispatch under a different admission label.

## Single-stream decode gains in both screens; the other cells are within noise

Both screens booted `L1a BA4 BA4 L1a` with the r27 audition SCREEN harness: decode at 1, 4 and 8 streams on code and prose, prefill TTFT at 8K and 30K tokens, one dense bf16 ladder per boot. Pair 1 is boot 1 against boot 2, pair 2 is boot 4 against boot 3. The c1 values are per-stream decode rates and the c4 and c8 values decode aggregates, the sum over the streams decoding together, in tokens per second. The harness's cell rule: NOISE if the control boots' spread exceeds any absolute paired effect (with a 3 % floor), otherwise WIN if every pair gains more than the noise, TIE if every pair is within it.

Screen 1's code c8 cell reads negative in both pairs and is decided NOISE only by its 6.3 % control spread; screen 2 does not reproduce it.

## Dense fidelity does not test the layer

The dense bf16 ladders of both screens covered 555,549 positions per boot. Perplexity relative to bf16 read +1.9018 / +1.9038 % on L1a and +1.9009 / +1.9007 % on BA4 in screen 1, and +1.9010 / +1.8555 % on L1a and +1.9009 / +1.9008 % on BA4 in screen 2. Top-1 agreement with bf16 read 0.90708 to 0.90710 on every boot. The ladders score teacher-forced prompts, which run through prefill with far more than four rows per call, where the layer returns to the original GEMM; these readings show that the image and its compiled graphs leave prefill numerics inside the L1a boot spread, not that the BA4 kernel is accurate.

## The kernel's error equals the correctly rounded product's

The kernel arm of the lean gate (2026-10-19 23:18 to 23:27 UTC, results `2026-10-19-231840-ba4-lean-gate`, `MODE=kernel`) booted the BA4 image in eager mode, with the KV pin lowered to 9.0 GB for eager activation headroom, and all 96 rank-layers ACTIVE. A test-only hook ([ba4_errstat_hook.py](../../scripts/r27-ba4-lean/ba4_errstat_hook.py), loaded through a `.pth` file so that the `vllm_ba4` files and their code hash stay unchanged) wrapped every live M=4 call BA4 served during greedy decode of 20 chunks at no context and 5 at 30,000 tokens plus the tool smoke. On the same operands it computed the exact product in fp64, the original GEMM's product and the best bf16 answer, the fp64 product rounded once to bf16, and accumulated per layer and rank. Every rank-layer saw at least 398,400 output elements.

| GEMM | mean \|error\| vs fp64 | mean signed error |
|---|---:|---:|
| BA4 | 0.00216633 | 1.1e-6 |
| original (cuBLAS) | 0.00216634 | 1.9e-6 |
| fp64 rounded once to bf16 | 0.00216633 | 1.1e-6 |

The rms errors are equal to six digits and the maximum absolute errors are identical. The worst layer's ratio of BA4's mean absolute error to the original GEMM's is 0.999998. The pre-registered rule ([kernel_decide.py](../../scripts/r27-ba4-lean/kernel_decide.py): aggregate mean and rms error at most 1.05 × the original's, no layer above 1.5 ×, bias bounded, 96 rank-layers covered) passed. Both GEMMs are within output rounding of the exact product; BA4's mean error equals that of the correctly rounded product to eight decimals, cuBLAS's is 1e-8 above it.

## Greedy decode differs from L1a; the pre-registered near-tie rule failed

The decode arm (2026-10-19 22:08 to 22:31 UTC, results `2026-10-19-220845-ba4-lean-gate` for the L1a arm, `2026-10-19-222356-ba4-lean-gate` for the BA4 arm) booted both arms through the serving launcher with the screen's knobs and ran [scripts/decode_fidelity.py](../../scripts/decode_fidelity.py) on 20 chunks of the dense corpus, 512 greedy tokens each, at no context and behind 30,000 tokens of context, twice on the L1a boot and once on the BA4 boot. Single-stream greedy decode runs every verify step at M=4, so this arm exercises the kernel on every step.

| comparison | chunks identical, ctx 0 | chunks identical, ctx 30K | p99 \|Δlogprob\| on agreed tokens, ctx 0 / 30K |
|---|---:|---:|---|
| L1a run 1 vs L1a run 2, same boot (control) | 20 / 20 | 11 / 20 | not gated |
| L1a run 1 vs BA4 | 1 / 20 | 3 / 20 | 0.31 / 0.43 |

The second L1a run at 30K is served from the prefix cache; three of its nine first divergences are not near ties, one at a top-1 lead of 6.75 nat. Most BA4 first divergences fall at near ties, but four do not: top-1 leads of 0.88 and 2.75 nat at no context, 1.38 and 0.75 nat at 30K. The pre-registered rule ([decide.py](../../scripts/r27-ba4-lean/decide.py)) required every BA4 first divergence to fall where L1a's top-1 leads its top-2 by at most 0.5 nat, so the arm reads FAIL on that rule; its activation check (48 of 48 layers ACTIVE and USED on both ranks) and tool smoke (5 of 5 on both arms) passed. An earlier run of this arm, in which a quoting error left the BA4 image's layer inactive on every rank, already diverged from L1a in 15 of 20 chunks at no context with a p99 of 0.125, so part of the divergence comes from the image and its compiled graphs rather than from the kernel.

A divergent greedy stream is the expected outcome of a one-ulp rounding difference in a recurrent layer, which the kernel test above measures. The 2026-08-28 XQA decode kernel diverged from FA2 on 16 of 20 chunks and was cleared by a T=0 GSM8K A/B ([R107](r107-xqa-nvfp4-decode.md)); BA4 was taken to the same two task A/Bs below, and the decision was the user's.

On 2026-10-19 one of the first eight BA4 boots (results `2026-10-19-r27-audition-profile-062521-3328625`) stopped with both workers silent after FlashInfer's autotune reload, before rank 0 logged its pooled workspace. ## Under the standard benchmark the layer costs about 5 ms of TTFT at 8 and 16 streams and 2 % of output at 16

The unpaired standard benchmark on the BA4 launcher read 1.4 to 6.8 % below L1a's at two to sixteen streams ([r27-ba4-std-bench](r27-ba4-std-bench.md)), so on 2026-10-20 three rounds paired BA4 on (B1) against `BA4=0` (B0) on the served image and launcher at the experiment port, where the `pcie_ipc` all-reduce stays off, ShareGPT V3 through the same client ([driver](../../scripts/r27-ba4-paired-std.sh)). Round 1 (02:51 to 03:32 UTC, results `2026-10-20-025104-r27-ba4-paired-std`, boots B1 B0 B0 B1) read +10.1 % output at 1 stream, −3.0 % at 8 and −3.9 % at 16, with TTFT p50 +9.5 and +7.8 %; each of its arms had loaded one warm compile artifact. Round 2 (04:08 to 04:57 UTC, results `2026-10-20-040845-r27-ba4-paired-std`, boots B1 B0 B0 B1 B1 B0) compiled every boot cold into its own caches: +10.0 % output at 1 stream, −0.4 % at 8 with the draws of the two arms interleaving, and at 8 streams TTFT p50 112.3 against 106.7 ms (+5.6 ms, +5.3 %, every B1 draw above every B0 draw) and TPOT p50 +2.7 %. By the rule written before round 2, the 8-stream throughput loss of round 1 and of the unpaired comparison is the compile artifact each arm loaded, not the layer. Round 3 (05:37 to 05:58 UTC, results `2026-10-20-053709-r27-ba4-paired-std`, boots B1 B0 B0 B1) re-ran 16 streams with cold compiles: output −2.0 % with both BA4 draws below both draws without it (ratio 0.980, on the rule's bound), against −3.9 % in round 1, and TTFT p50 +5.0 ms. The TTFT cost at 8 and 16 streams is the layer's, and its mechanism is not identified. A cold compile takes 67 to 70 s with BA4 against 26 to 27 s without. Per-boot tables: [r27-ba4-std-bench](r27-ba4-std-bench.md#paired-rounds-against-ba4-switched-off).

## Reproducing it

`BA4=1 bash scripts/build-v031-image.sh` builds the image from a clean clone: the L1a chain, its inventory check against the served L1a image, then [patches-v0310/ba4/Dockerfile](../../patches-v0310/ba4/Dockerfile) on top ([patches-v0310/README.md](../../patches-v0310/README.md#ba4-builds-from-the-checkout-and-admits-itself-per-host)). On 2026-10-20 all eight source files the layer's installer pins (three it edits, five it must leave unchanged) carry the hashes of the served L1a inventory, which a clean-clone build matched on 2026-10-19 ([r27-l1a-build-verify](r27-l1a-build-verify.md)). A clean-clone build in an empty Docker daemon on 2026-10-20 matched the served BA4 image: its 7,138-file inventory, every source and every `vllm_ba4` file are identical, and the one differing shared object, the nvcc-recompiled NVFP4-KV overlay, differs in 3 bytes of a temporary-file name ([r27-ba4-build-verify](r27-ba4-build-verify.md)). The inventory the script derives for BA4 equals the served BA4 image's line for line.

The layer is active only with reports produced on the host that serves it: the fingerprint names the cards' UUIDs and the reports name the weight bytes and code hash. The profile runs and qualifier that produce them belong to the serving host's audition harness and are not in this repository. Without reports, [scripts/serve.sh](../../scripts/serve.sh) leaves `VLLM_SM12X_BA_M4` unset and the BA4 image computes as the L1a image does; with `BA4_INPUTS` pointing at reports that do not match the host, every layer logs INACTIVE and runs the original GEMM.

Rollback is [scripts/serve-v031-l1a-daily.sh](../../scripts/serve-v031-l1a-daily.sh). The decode and prefill curves on the BA4 launcher are in [r27-ba4-curves](r27-ba4-curves.md) (2026-10-19, results `2026-10-19-233406-r27-ba4-curves`); the standard serving benchmark on it is in [r27-ba4-std-bench](r27-ba4-std-bench.md) (2026-10-19 to 2026-10-20, results `2026-10-19-r27-ba4-std-bench-2335`), which reads +11.6 and +11.8 % against L1a at one stream and 1.4 to 6.8 % below it at two to sixteen streams; the paired rounds above attribute that throughput gap to the compile artifact.
