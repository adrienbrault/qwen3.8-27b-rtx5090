Patch 0146 issues one non-blocking device-to-host copy of the sequence lengths per decode step into a pinned buffer, records an event, and hands every consumer of the deprecated `seq_lens_cpu` property the same host tensor after one event wait. The R190d census on the served step, knob off against knob on, on one compile artifact: target phase 5 blocking copies plus 1 graph replay become 1 event synchronize plus 1 replay; the drafter's own copy, its replay and the output readback stay; 9.00 syncs per step become 5.00, over 100 steps each. The greedy decode ruler, knob on against knob off on the same loaded artifact (same three compile hashes, nothing saved), agrees on 20 of 20 chunks with median and p99 0 at ctx 0 and at 30K, so the host values are the same numbers.

Steps per second, off then on (a second image pair with the census patch reads the same direction): code 1 stream 75.4 then 70.2, prose 1 stream 75.5 then 71.6, code 8 streams 370.8 then 353.0, code 16 streams 485.1 then 469.3. The five blocking copies were not on the critical path: by the time the host reached them the stream had drained, so they cost nothing, while the early copy and the wait at the first consumer remove the overlap the metadata build had. BRIEF29's own falsifier applies: the 4.09 ms no-kernel gap in the single-stream step (R183) is not bound by these syncs. The knob stays off; the next step on this route is a host-side trace of one decode step that names what fills the gap, not another sync patch.
